Branch feat/vm-target · for Gowtham

nextship now deploys to any Linux server, not just App Platform

Version 1.0.2 could take a Next.js app to one place: DigitalOcean App Platform. This branch adds a second target, any Ubuntu or Debian machine reachable over SSH, and gives it the full lifecycle: setup, zero-downtime deploys behind Caddy with HTTPS, rollback, env, domains, logs with history, images, destroy, status, reboot and moving between servers. Every DigitalOcean behaviour stays as it was.

Before: 1.0.2

One platform, one app per App Platform app.

  • Needs a DigitalOcean API token
  • ISR cache and optimized images lost on every restart
  • The CDN can keep serving a page after revalidatePath
  • Logs of a replaced deployment are gone
  • The Server Actions key lives on one laptop

After: this branch

Any VPS or cloud VM, many apps per server.

  • Needs only an SSH key, no cloud token
  • ISR pages and optimized images survive restarts
  • No CDN in the way, so revalidation reaches visitors
  • logs --deployment reads replaced deployments
  • The key lives on the server, shared by laptop and CI

Every new feature

Grouped by what a user is trying to do. Everything marked new exists only for the server target unless it says otherwise.

server add new

Turns a fresh Ubuntu 22.04, 24.04 or Debian 12 box into a deploy target in about a minute. Pins its SSH host key.

Remote and local builds new

--build remote uses the server's Docker through an SSH tunnel; --build local builds here and streams the image.

Zero-downtime deploys new

Health-gated switch through Caddy. A failed deploy leaves the old version serving and prints the new container's last 50 log lines.

Automatic HTTPS new

domain add writes a Caddy site; Caddy gets the certificate once DNS points at the server. A DNS pre-check warns first.

Rollback on a server new

Starts an earlier image through the same health-gated sequence.

Env without downtime new

env push and env rm rewrite a 0600 file on the server and restart the live image with no dropped request.

logs --deployment new

Reads a replaced deployment's output from the journal, by deployment id or image tag.

Cache that survives restarts new

Regenerated ISR pages in a per-image volume, optimized images and fetch cache in a per-app volume.

Server-held Server Actions key new

Laptop and CI build with the same key. Disagreement is refused, never silently resolved.

Images and auto-prune new

Keeps the newest 5 served deployments after every deploy; --gc trims build cache to 5 GB.

Many apps per server new

Each gets its own domains, memory share and state directory. destroy removes one and leaves the rest.

server status new

Server health plus every app, with warnings for low disk, stray published ports, outdated setup and unhealthy apps.

server reboot new

Reboots and waits until every app that was running is healthy again, up to 10 minutes.

server move new

Moves the app, env, key and domains to another server; nextship.json switches only once it serves there.

Self-healing new

Docker restarts crashed apps; a watchdog timer restarts apps that hang with failing health checks.

Disk and memory guards new

Deploy refuses under 3 GB free; remote builds refuse under 2 GB RAM; containers get a fair memory limit.

doctor knows the target both targets

DigitalOcean-only advice stays DigitalOcean-only; server projects get single-server and request.url warnings.

End-to-end conformance new

conformance/vm/e2e.sh runs the whole lifecycle against a real SSH server, and a vm CI job runs it.

What changed in the code

In 1.0.2 there was already a Target interface, but commands still carried DigitalOcean knowledge: deploy printed App Platform plan lines and pushed to a registry, logs opened App Platform's websocket, images and destroy warned about registry garbage collection, env push said values go to "your DigitalOcean account". A second target would have meant editing every command.

Phase 0 moved all of that behind the interface. Commands now ask the driver for its plan lines, build platform, Docker daemon, image delivery, log stream, storage wording, destroy plan and Server Actions key. Against a stubbed API, main and the branch print byte-identical output for 20 DigitalOcean commands, which is how "nothing changed for DigitalOcean" was checked rather than assumed.

Setting up a server

nextship server add root@203.0.113.10 prints a plan and changes nothing. The same command with --yes applies it. Order matters here: it is designed so the user cannot be locked out.

Before anything changes

  1. Parse and validate the address

    user@host[:port], IPv6 in brackets. A host starting with a hyphen, a space or anything shell-like is refused.

  2. Scan and fingerprint the host key

    ssh-keyscan, strongest key first (ed25519, then ECDSA, then RSA). The SHA256 fingerprint is printed so it can be compared with the provider's console. If nextship.json already pins a different key for this server, it stops.

  3. Connect and check sudo

    Through the user's own ssh, batch mode, no passwords, strict checking against the scanned key. Refuses if the user lacks passwordless sudo.

  4. Run the setup plan as root

    setup.sh travels over stdin and runs plan: every step checks and reports ok, CHANGE, skip or REFUSE. Nothing is copied onto the server.

Afterwards the plan runs again and every step must report ok. Then nextship.json records target: "vm" and the server with user: "nextship", its pinned key line and its architecture. A second server add changes nothing; running it from another project just records the same server.

From source to image

The build pipeline is the part both targets share. What the VM target changes is where it runs, which CPU it builds for, and where the Server Actions key comes from.

> Plan target your server 203.0.113.10, arm64, Docker 29.8.0 build on the server's Docker 29.8.0, for linux/arm64, over SSH image kept on the server as acme-web:<deployment id> app UPDATE "acme-web" (354832e1-…), which nextship created memory up to 6268m of 7836 MiB address http://203.0.113.10 switch Caddy moves traffic only once the new container is healthy; until then the current one serves untouched 1 existing app(s) on this server

  1. Read the plan deploy.ts, vm-target.ts

    One SSH round trip reads RAM, free disk, Docker version and the default app. Refuses under 3 GB free, refuses a remote build under 2 GB RAM, refuses an app name that exists on the server but was not created by this project. Nothing past this point runs without --yes.

  2. Detect the project detect.ts unchanged

    Finds the project and workspace roots, the installed Next.js version, package manager, lockfile, build command, Node major and env files, all from disk.

  3. Resolve the Server Actions key actions-key.ts new

    A decision table, so a key is never rotated silently:

    • NEXT_SERVER_ACTIONS_ENCRYPTION_KEY set: use it, warn if the server's differs
    • Server has one, no local file: use the server's
    • Local file only: upload it to the server
    • Both exist and differ: refuse
    • Neither: generate once, store only on the server

    It travels over SSH stdin into a 0600 file, never on a command line.

  4. Choose where to build vm-target.ts builder() new

    Remote (default): opens ssh -L local.sock:/var/run/docker.sock with the same pinned key and sets DOCKER_HOST to it. Docker on your machine becomes a client of the server's daemon, so the build runs natively on the server's CPU and only the build context leaves your machine. Plain DOCKER_HOST=ssh:// was avoided because it bypasses the pinned key.

    Local: the local daemon builds with --platform linux/<server arch>.

  5. Prepare the context and identity prepare.ts, identity.ts unchanged

    Writes a generated .nextship/Dockerfile and ignore file, copies the adapter and prune script in, and computes the deployment id: dpl-<commit>-<digest> over the Dockerfile, helpers, key and env files, so two different images never share a tag.

  6. Builder stage docker build --target manifest unchanged

    • Copies manifests before sources so edits do not re-run the install; package store and Next.js cache are BuildKit cache mounts
    • Runs the project's own build with the adapter injected via NEXT_ADAPTER_PATH; next.config.js is never touched
    • Env files, the key, .npmrc are secret mounts that never enter a layer
    • Prunes to /out from Next.js's trace files and writes server.cjs, replacing standalone output
    • Exports manifest.json; a build whose manifest lacks the deployment id fails

    On a server, the Next.js build cache is now named by app and server, so a laptop and CI share one warm cache there.

  7. Runtime stage docker build --target runtime unchanged

    node:<major>-slim, tini as PID 1, jemalloc for sharp, npm removed, non-root user, a HEALTHCHECK, node server.cjs. Served mostly from the builder stage's cache.

  8. Deliver the image vm-target.ts deliverImage() new

    Remote: already on the server, tagged <app>:<deployment id>. Local: docker save | ssh docker load through a pipeline that checks both exit codes, so a transfer that died half way cannot pass as a load. App Platform still pushes to its registry here.

Why the cache survives

Measured with docker diff: ISR rewrites files under .next/server/app, the image optimizer writes .next/cache/images. Two named volumes hold them:

nextship-<app>-build-<image>
Mounted over .next. Regenerated pages belong to one build, so a restart, env change or rollback to that image keeps them, but a new build never serves an old build's pages. Removed with its image.
nextship-<app>-cache
Mounted over .next/cache. Optimized images and the fetch cache, shared across deployments the way Next.js shares .next/cache between builds.

Every other command, step by step

Same flags and plans as on App Platform, with a different mechanism underneath. Open any one.

nextship rollbackreturn to an earlier image
  1. Reads deployments.json and offers deployments that served before.
  2. The plan says the current env file is used, not the one that deployment first had.
  3. Checks the image still exists on the server; a pruned one is refused with how to rebuild it.
  4. Runs release steps 1 to 7 with that image, recorded as rollback to <id>.
nextship env push / env rmchange runtime variables
  1. Reads the project's env files through Next.js's own loader, as before.
  2. Plans add or update per key, and says values are readable by the server's root and nextship users.
  3. Refuses a value with a line break, which Docker's env file cannot hold.
  4. Under the lock, rewrites /etc/nextship/apps/<app>/env from stdin with mode 0600.
  5. Runs the release sequence with the same live image, so the new env takes effect with no downtime. Measured: 40 of 40 requests answered 200 during the switch.
nextship domain add / domain rmattach a hostname with HTTPS
  1. Validates the domain and resolves it; warns if it does not point at the server yet.
  2. Under the lock, computes the domain list (the first domain is always primary).
  3. Renders and validates the Caddy site, reloads Caddy, and only then records the domain in app.json, so a domain Caddy refused is never recorded.
  4. Prints the A record, plus an AAAA note when the server has IPv6.
  5. Caddy requests the certificate once DNS resolves. nextship domain reports it live only when a real TLS handshake presents a valid certificate.
nextship logslive output and history
  • logs: docker logs --tail 500 of the live container.
  • logs --follow: streams docker logs -f over SSH; Ctrl+C stops it cleanly.
  • logs --deployment <id or tag>: journalctl CONTAINER_NAME=<container>, so a replaced deployment's output is still there until the 500M journal rotates it out.
nextship images / images prunewhat is stored on the server
  • images lists this app's images: deployed now, or kept for rollback.
  • images prune --keep N removes older images with their stopped containers and build volumes. The live image is never removed.
  • After every successful deploy, images beyond the newest 5 served deployments are pruned automatically.
  • --gc trims Docker's build cache to 5 GB.
nextship destroy <app>remove one app and nothing else
  1. Needs the app name and --yes, as before.
  2. The plan lists what goes and what stays: the server, Caddy, every other app and DNS.
  3. Under the lock: removes containers labelled with this app, removes its site (validated and reloaded), releases the default address if it held it, removes its volumes and /etc/nextship/apps/<app>.
  4. With --images, removes its images too. Clears appId from nextship.json.
nextship server statushealth of the server and every app
  • Server: OS, uptime, reboot required, load, memory, disk, Docker and Caddy versions, setup version.
  • Per app: live deployment, health, restart count, memory use, domains and certificate state.
  • Warns on under 3 GB free, ports published around Caddy, outdated setup, pending reboot, unhealthy app.
nextship server rebootprove every app comes back
  1. Records a boot marker (kernel boot id and PID 1's start time) and the running containers.
  2. Runs sudo systemctl reboot, the only command nextship may run through sudo.
  3. Polls SSH every 5 seconds until the boot marker changes.
  4. Waits until every container that was running is healthy, up to 10 minutes in total.
nextship server move user@newhostrelocate an app
  1. Reads from the old server into memory only: app record and domains, env file, key, live deployment.
  2. Runs the full server add flow on the new host.
  3. Writes the record, env and key to the new server, never to local disk.
  4. Streams the exact live image: ssh old docker save | ssh new docker load, no rebuild.
  5. Runs the release sequence there and waits for healthy.
  6. Only then updates nextship.json; a failure earlier leaves the project pointed at the old server.
  7. Prints the DNS records to change. The old server is only read and keeps serving until destroyed there.

Safety guarantees

The same stance as App Platform, extended to a machine nextship has root on.

Nothing surprising

  • Nothing changes without --yes; a plan always prints first
  • Only the app whose id matches nextship.json is touched
  • Only containers labelled sh.nextship.managed and sh.nextship.app=<name> are stopped or removed
  • The Docker daemon's config, other workloads and DNS are never modified
  • A failed deployment leaves the previous one serving

Nothing exposed

  • Host key pinned; a changed key is a hard error, never a prompt
  • Your own ssh, batch mode, no passwords; nextship never reads a private key
  • No shell interprets anything on your machine; remote values are validated or single-quoted, tested with hostile input
  • Secrets travel only on stdin into 0600 files, never on a command line or in a layer
  • Setup cannot lock you out: login proven before hardening
Worth saying out loud: the nextship user is in the docker group, which is root-equivalent. Anyone holding its keys controls the server. The plan warns about this, and the docs say it plainly.

What sits on the server

/etc/nextship/ owned by nextship, 0700 server.json setup version that last ran default-app app answering http://<server> caddy/Caddyfile imports sites/*.caddy caddy/sites/<app>.caddy generated per app apps/<app>/app.json id, name, domains: the ownership record apps/<app>/deployments.json history for rollback apps/<app>/env runtime variables, 0600 apps/<app>/secrets Server Actions key, 0600 apps/<app>/lock/ present only during a change /usr/local/lib/nextship/watchdog.sh plus its systemd timer /etc/sudoers.d/nextship systemctl reboot only Docker network nextship · nextship-caddy · <app>-r… containers volumes nextship-<app>-build-<image>, nextship-<app>-cache, caddy data and config

Two of these exist nowhere else and should be backed up: the env and secrets files. Everything else is either in the repository or regenerated.
